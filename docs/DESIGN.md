# OtoTag 試作設計書

作成: 2026-11-27（同日改定: Windows 版・GitHub 公開・フォルダ一括処理・ファイル名変更を追加 / アプリ名と対応形式を決定）
状態: 設計のみ。コードはまだ書いていない。
アプリ名: **OtoTag**（「音」+ Tag）。GitHub リポジトリ: `yyoossk/ototag`（2026-11-27 時点で空きを確認）。Android パッケージ: `com.yyoo.ototag`（UniPatcher の命名規則に合わせる）。
試作の対応形式（決定）: **MP3 / FLAC / M4A・MP4 / OGG Vorbis / Opus の5形式**。FLAC・OGG・Opus は同じ Vorbis Comment の経路で書けるため、3形式に絞るより追加コストが小さい。WAV / AIFF / WMA / DSF は後回し（WAV は RIFF INFO と ID3 の二重規格でプレイヤーごとの対応が割れるため）。
対象: Android + Windows、GitHub で公開する。
中心サービス: MusicBrainz + Cover Art Archive、補助: AcoustID（任意）

---

## 1. 試作で検証すること

一番のリスクは「メタデータが取れるか」ではなく「Android 上で実ファイルのタグを安全に書き換えられるか」。
なので試作は次の順で潰す。

1. 1ファイルを手で編集して保存し、他のプレイヤーで書き換わったことが確認できる（MP3 / FLAC / M4A）。
2. MusicBrainz の検索候補から選んで、差分を見てから一括で適用できる。カバー画像も埋め込める。検索の入口は既存タグとファイル名の両方。
   あわせて、検索を使わない手動編集でも保存までできる。
3. アルバム単位で release を引き、全曲にトラック番号どおり適用できる。
4. （後段）タグが空のファイルを AcoustID の指紋で特定できる。

試作に入れないもの: 歌詞取得、ファイル名の自動リネーム、MusicBrainz へのデータ投稿、再生機能。

## 2. 方式の決定（Kotlin Multiplatform で Android + Windows を1つのコードに）

今回は **Kotlin Multiplatform（KMP）+ Compose Multiplatform** にする。いつもの Go + WebView ではない。

- タグ書き込みの決定打が JVM 系にしかない。jaudiotagger 系は MP3（ID3v1/v2）・MP4/M4A・Ogg Vorbis・FLAC・WAV・AIFF・DSF・WMA まで読み書きできる。その KMP 派生（jaudiotagger-kotlin、Maven Central 配布）は **Android / JVM（= Windows デスクトップ）/ iOS / macOS で読み書きのコードを共有**でき、Android ではファイルディスクリプタ経由の I/O（SAF / MediaStore 対応）を持つ。つまりタグ処理・MusicBrainz 検索・ファイル名パース・リネーム規則を全部共有したまま、Android アプリと Windows アプリ（JVM デスクトップ）の両方を出せる。
- Go 側のタグライブラリは読み取り中心で、書き込みは MP3 の ID3v2 程度しか実用にならず、FLAC / MP4 で詰まる。従来方式に固執すると Windows 版だけ別実装になる。
- ファイルアクセスはプラットフォーム別に薄く分ける: Android は SAF / MediaStore、Windows は通常のファイルパス + ドラッグ&ドロップ。共有側は「ファイルの読み書き口」インターフェースだけを見る。
- Chromaprint（指紋生成）は Android は NDK の libchromaprint、Windows は fpcalc 同梱、とプラットフォーム別でよい（後段の任意機能なので試作の本体に影響しない）。

検討した代替案:

| 案 | 不採用理由 |
|---|---|
| Go + WebView（従来方式） | タグ書き込みライブラリが弱く、FLAC / M4A の書き込みで詰まる。Windows と Android で中身が割れる |
| TagLib を JNI / JNA で使う | 対応形式は最強だがネイティブビルドと橋渡し層の自作が重い。jaudiotagger で不足が出たら再検討 |
| MediaStore の値を書き換える | MediaStore は端末内の索引データベースで、ファイル本体のタグは書き換わらない。他の端末・プレイヤーに持ち出せない |
| Android と Windows を別々に作る | 検索・パース・書き込み規則が二重になり、片方だけ直す事故が起きる |

## 3. 画面構成

- **ライブラリ**: 対象の音楽ファイルの一覧（3.5章）。タグ不足（曲名なし・カバーなし等）をバッジで示す。フォルダ / アルバムで絞り込み。複数選択で一括処理（検索して適用・共通項目の手動編集・ファイル名変更・カバー一括投入）ができる。
- **編集**: 1曲の現在のタグを表示し、**そのまま手動で編集できる**（4.5章）。MusicBrainz 候補との差分（現在値 → 候補値）を並べて見せ、項目ごとに採用 / 却下できる。候補を採用した後も、保存前に手で直せる。
- **候補選択**: 検索結果のリスト。スコアだけでなく発売年・国・トラック番号・曲の長さを表示し、ユーザーが選ぶ。**選んだ候補がそのままタグに入る**（カバー画像を含む）。
- **設定**: 言語、AcoustID のユーザーキー、書き込み前のバックアップ保持期間、ID3v2 の版（既定 v2.3）。

## 3.5 対象ファイルの指定と一覧・複数選択（一括処理）

対象の決め方はプラットフォームごとに用意し、一覧以降の操作は共通にする。

**Android**
- **フォルダ指定**: SAF（OpenDocumentTree）でフォルダを選ぶ。許可は保存し、次回も同じフォルダを開ける。中はサブフォルダを含めて走査し、音楽ファイルだけを一覧に出す。
- **単体指定**: ファイルピッカー（OpenDocument、複数可）で1つから選べる。
- **端末全体**: MediaStore から端末内の音楽を一覧に出す入口も残す（フォルダを指定しなくても使える）。

**Windows**
- **フォルダ指定 / ファイル指定**: フォルダ選択・ファイル選択ダイアログ（複数可）。
- **ドラッグ&ドロップ**: ウィンドウへ音楽ファイルやフォルダを落としたら対象に追加する（フォルダはサブフォルダを含めて走査）。詳細は 4.7章。

**一覧と一括処理（共通）**
- 一覧の各行: カバー（あれば）、曲名、アーティスト、アルバム、形式、長さ、タグの状態バッジ（カバーなし / 曲名なし / MBID あり等）。列でソート、文字列で絞り込み。
- 複数選択 → 一括でできること:
  1. **検索して適用**: アルバム単位でまとまっている場合は release を1回だけ引いて全曲へ配る（レート制限対策を兼ねる）。バラバラの曲の集まりは曲ごとに検索キューへ入れ、候補は曲ごとに確認する。
  2. **共通項目の手動編集**: アルバム名・アルバムアーティスト・ジャンル・年などをまとめて書き換え（4.5章）。
  3. **ファイル名の一括変更**: タグから作る命名パターンでまとめて改名（4.6章）。
  4. **カバーの一括投入**: 選択した画像を、選んだ全曲のカバーにする（アルバム単位の作業用）。
- 一括処理は途中経過（何曲中何曲・失敗した曲と理由）を表示し、失敗した曲だけ残して再試行できる。全部成功するまで他を巻き込まない（1曲の失敗で全体を止めない、成功分は確定する）。

## 3.6 言語対応

- 対応言語は従来のアプリと同じ **12言語（ja / en / fr / de / it / es / ru / pt / pl / ko / zh-Hans / zh-Hant）**。
- 言語の決め方は従来どおり: **保存済みの選択 → システム言語 → en**。つまり初期状態（未選択）では端末のシステム言語で起動し、設定で変えたらそれを保存して次回から使う。
- アプリ内の文言は表示中の1言語だけで出す（日英併記はしない。従来のルールどおり）。
- MusicBrainz 側の表示名は、言語に合わせてアーティストの別名（alias）から寄せる。例: 日本語表示なら locale=ja の primary alias（米津玄師）を優先し、英語表示なら Kenshi Yonezu を優先する。タグへ書く値もその表示名を初期値にするが、編集画面で手直しできる。

## 4. 特定の3経路

- **経路A（主）: 既存タグから検索** — 曲名 + アーティスト + アルバムで MusicBrainz の recording を検索する。
- **経路B（主）: ファイル名から検索** — タグが空・文字化け・間違っているファイルはこちらが本命。ファイル名と置かれているフォルダ名から手がかりを拾って検索し、**出てきた候補をユーザーが選択したら、その候補の値がタグに入る**（カバー含む）。流れは経路Aと共通（候補選択 → 差分確認 → 保存）。
  - パース規則（よくある命名をカバーする）:
    - トラック番号の接頭辞: `01. 曲名` / `01 - 曲名` / `01_曲名` → 番号を分離してトラック番号の手がかりにする
    - 区切り: `アーティスト - 曲名` / `曲名 - アーティスト`（両方向を候補クエリにする）、`アーティスト／曲名`、`[アーティスト] 曲名`
    - 括弧内の付帯情報: `曲名 (feat. ○○)` / `曲名 [Remix]` は曲名本体と付帯に分けて両方で引けるようにする
    - フォルダ名の利用: 親フォルダが `アルバム名`、その上が `アーティスト名` という配置が多いので、フォルダ名をアルバム / アーティストの手がかりとして検索クエリに加える
    - ノイズ除去: 拡張子、サイト名・宣伝文句らしい角括弧、ビットレート表記（`[320kbps]` 等）は検索語から落とす
  - パース結果は検索画面に「ファイル名から拾った値」として表示し、検索する前にユーザーが直せる（例: アーティストと曲名が逆だった場合）。
  - タグとファイル名の両方に手がかりがある場合は両方を合わせたクエリも作り、候補の並べ替えに使う（長さ・トラック番号の一致を優先）。
- **経路C（任意・後段）: AcoustID 指紋** — 音そのものから特定する。タグもファイル名も無いファイル用。

候補の自動確定はしない。実測（付録）でも、検索1位が求めている盤とは限らない（「Lemon / 米津玄師」の1位はライブ映像盤だった）。スコア + 曲の長さの差（±3秒以内を優先）+ 既存タグとの一致度で並べ替えまでは自動でやり、最後は候補選択画面でユーザーが決める。

## 4.5 手動編集

検索に頼らず、ユーザーが直接タグを書き換える仕組みも最初から入れる（検索で見つからない同人・未登録曲はこれが唯一の手段になる）。

- 編集できる項目: 曲名、アーティスト、アルバム、アルバムアーティスト、作詞、作曲、ジャンル、年（発売日）、トラック番号 / 全曲数、ディスク番号 / 全枚数、コメント、ISRC、カバー画像。
- カバー画像は端末の画像ピッカーから選んで差し替え / 削除できる（長辺1200pxへの縮小は 6章 の規則どおり）。
- **複数ファイルの一括編集**: ライブラリで複数選択し、共通項目（アルバム名、アルバムアーティスト、ジャンル、年など）だけをまとめて書き換えられる。曲名のような曲ごとの項目は一括対象にしない。
- 項目を空にして保存したら、そのフィールドはタグから削除する（空白文字で埋めない）。
- 保存は即ファイルへは書かず、まず変更一覧（どの項目がどう変わるか）を見せてから実行する。実行後の検証と「元に戻す」は 6章 の書き込み手順に従う。
- MusicBrainz 候補を採用した値も、保存前ならこの画面で自由に手直しできる（検索結果が正解とは限らないため）。

## 4.6 ファイル名の変更

タグだけでなく、**ファイル名そのものもこのアプリで変更できる**ようにする。

- **手動変更（単体）**: 編集画面にファイル名の欄を置く。拡張子は欄の外に出して固定（`.mp3` 等を消したり変えたりできない）。保存時にタグ書き込みと一緒に改名する。
- **一括変更（パターン）**: 複数選択した曲を、タグから作る命名パターンでまとめて改名する。例: `%track% - %title%`、`%artist% - %title%`、`%album%/%disc%-%track% %title%`。実行前に新旧一覧のプレビューを出し、同名衝突がある行は赤く示して実行させない。
- 安全規則:
  - 使用できない文字（Windows の `\ / : * ? " < > |` と制御文字）は自動で置換し、置換したことをプレビューで見せる。Windows 版がある以上、Android 側でも同じ規則で統一する（ファイルを PC へ移したときに壊れないため）。
  - 同じフォルダ内に同名が既にある場合は上書きしない。連番を付けるか中止するかをユーザーが選ぶ。
  - 末尾の空白・ドット、長すぎる名前（255バイト目安）もチェックする。
  - 改名はタグのバックアップとは別に「元の名前」を履歴に残し、直後なら元に戻せる。
- 実装メモ: Android は SAF の rename（DocumentsContract.renameDocument）/ MediaStore の DISPLAY_NAME 更新、Windows は通常のファイル移動。どちらも「タグ書き込み → 検証 → 改名」の順で、改名に失敗してもタグ変更は確定済みの状態として扱い、失敗を一覧に出す。

## 4.7 画像の手動投入と Windows のドラッグ&ドロップ

- **画像の手動投入（共通）**: カバーは検索で自動取得する以外に、ユーザーが手で入れられる。
  - Android: 画像ピッカー / ファイルピッカーから選ぶ。
  - Windows: ファイル選択に加え、**編集画面のカバー欄へ画像ファイルをドラッグ&ドロップ**でも入る。
  - 入れた画像は長辺1200pxに縮小してから埋め込む（6章）。複数選択中は選んだ全曲へ同じカバーを一括投入できる（3.5章）。
- **Windows のドラッグ&ドロップ**:
  - 音楽ファイル → 一覧に対象として追加。
  - フォルダ → サブフォルダを含めて走査し、音楽ファイルを追加。
  - 画像ファイル → (a) 一覧画面に落としたらカバー候補として保持し選択中の曲へ、(b) 編集画面のカバー欄に落としたらその曲のカバーに設定。
  - ドラッグ中は「ここに落として追加」と分かる表示を出し、対応外の形式は落とした時点で理由付きで知らせる。
- Android にはドラッグ&ドロップは出さない（従来のルールどおり、タップで選ぶ形に差し替える）。

## 5. MusicBrainz API 設計（実測済み）

- ベース: `https://musicbrainz.org/ws/2/`、読み取りは API キー不要、`fmt=json` を付ける。
- **User-Agent が必須**: `MusicTagEditor/0.1 (連絡先URL)` の形。無い・汎用のものは弾かれる。
- **レート制限は 1リクエスト/秒**。アプリ全体で単一キューにし、間隔は 1100ms を確保する。503 が返ったら指数バックオフで再試行。一括処理の所要時間はこの制限が支配する（アルバム12曲でも、release を1回引けば済む設計にする＝曲ごとに引かない）。
- 使用エンドポイント:
  - 検索: `GET /recording/?query=recording:"…" AND artist:"…"&fmt=json`（Lucene 記法。引用符と特殊文字のエスケープが必須）
  - 盤の全曲取得: `GET /release/{MBID}?inc=recordings+artist-credits+labels&fmt=json`
  - カバー: `GET https://coverartarchive.org/release/{release MBID}/front-500`（一覧は 250 / 500 / 1200、埋め込み用は 1200 か原寸。実体は archive.org への 307 リダイレクトなので、クライアントはリダイレクト追従が必須。カバーが無い盤は 404 で、これは正常系として扱う）

フィールド対応（MusicBrainz → タグ）:

| MusicBrainz | タグ項目 | 備考 |
|---|---|---|
| recording.title | 曲名 | |
| artist-credit | アーティスト / アルバムアーティスト | joinphrase（feat. 等）を保持して連結 |
| release.title | アルバム名 | 候補選択で決まった release のもの |
| release.date | 年（発売日） | 年だけの盤もある |
| media[].track[].number / position | トラック番号 / 全曲数 | ディスク番号は media の position |
| work の関係・recording の関係 | 作詞・作曲 | 取れる場合のみ。inc に rels 系を追加 |
| recording.isrc-list | ISRC | |
| release-group / recording の genres | ジャンル | 票数の多い順に先頭だけ採用も可 |
| recording.id / release.id | MBID | ファイルに保存する（ID3 は UFID / TXXX、FLAC は MUSICBRAINZ_* キー）。再検索が一発になる |

取得結果は MBID をキーに端末内へキャッシュし、同じ盤を二度引かない。

## 6. タグ書き込み設計

- ライブラリ: jaudiotagger-kotlin（LGPL 2.1。ライブラリ自体を改変しなければアプリ側は問題なし）。
- 書き込み手順（安全側に倒す）:
  1. 元ファイルをアプリのキャッシュへコピー（バックアップ）。
  2. 一時ファイル側でタグを書き換える。
  3. 書き換えた一時ファイルを読み直し、意図したフィールドになっているか検証する。
  4. SAF 経由で元へ上書きし、MediaScanner で再スキャンして他プレイヤーに反映させる。
  5. 失敗したら元ファイルを復元する。保存後も一定期間は「元に戻す」を可能にする。
- 文字コード: ID3v2.3 + UTF-16 を既定にする（古いプレイヤー・カーナビとの互換優先）。FLAC は Vorbis Comment（UTF-8）、M4A は MP4 アトム。
- カバー埋め込み: JPEG を基本とし、長辺 1200px 上限で取り込む（原寸数MBの画像をそのまま入れるとプレイヤーによっては表示が壊れる）。

## 7. プラットフォームの制約

Windows 側は通常のファイルシステムで制約は少ないが、プレイヤーが再生中のファイルはロックされて書けない場合がある。その場合はその曲だけ失敗として一覧に出す（3.5章の一括処理の規則どおり）。

Android 側:

- 権限: 音楽の読み取りは `READ_MEDIA_AUDIO`（Android 13+）。フォルダ単位の書き込みは SAF（OpenDocumentTree）でユーザーに許可してもらう。
- 他アプリが作ったファイルの書き換えは、実行時にユーザー承認（RecoverableSecurityException のダイアログ）が必要な場合がある。試作の合格条件に「他プレイヤーが置いたファイルでも書けること」を入れる。
- 対象: minSdk 26 / target は最新の実機（Galaxy S25 Ultra）で検証する。

## 8. AcoustID の注意（2026-11-27 時点で公式ページ確認）

- 無料利用は**非商用のみ**。商用アプリは別契約。→ 公開形態（自分用 / 無料公開 / 有料）が決まるまでは任意機能として切り離す。
- 開発者用の application key（client）とは別に、利用者ごとの user key の仕組みがある。公式ページでは **2027-01-01 から lookup にも user key が必須**になる予定と案内されている。→ 設定画面でユーザー自身のキーを入れてもらう設計にしておき、アプリに他人のキーを埋め込まない。
- レート制限は 3リクエスト/秒（MusicBrainz より緩い）。
- 指紋生成: MediaExtractor + MediaCodec で端末標準デコーダを使い、先頭最大120秒を 11025Hz モノラル PCM にして libchromaprint（NDK 同梱）へ渡す。FFmpeg を同梱しないので APK が軽い。うまく行かない形式があった場合の代替は fpcalc（arm64）を `libfpcalc.so` として同梱する方式（kaiHEN Android 版の libnode.so と同じ手口）。

## 10. GitHub 公開と配布

## 11. 決定事項（2026-11-27、ユーザー委任により決定）

1. アプリ名は **OtoTag**、リポジトリは `yyoossk/ototag`。候補だった TuneTag / TagTune 系は既存の Mac / iOS 向けタグ編集アプリが同名で存在するため不採用。OtoTag は同名の音楽アプリが見当たらず、GitHub の yyoossk 配下も空いていることを確認した。
2. 試作の対応形式は **MP3 / FLAC / M4A・MP4 / OGG Vorbis / Opus**（冒頭参照）。Phase 0 のスパイクは MP3 / FLAC / M4A で書き込み経路を確定させ、同じ Vorbis Comment 経路の OGG / Opus を続けて確認する。
3. 競合メモ: Android には AutomaTag（Automatic Tag Editor）という近いアプリがあり、タグ・ファイル名からの検索や MusicBrainz 参照もしている。OtoTag の差別化は「無料・オープンソース（GitHub 公開）・広告なし・Windows 版と同一機能・ファイル名変更まで含む」点に置く。
